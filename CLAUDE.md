# Padel Park Gran Jardín — Tarjeta de Lealtad

Loyalty card PWA for a padel club. Plain React 18 (UMD build) + Babel
standalone loaded via CDN `<script>` tags — no build step, no bundler.
Two separate single-page apps sharing the same Supabase backend:

- `Landing Page.html` + `app.jsx` — member-facing app
- `Admin.html` + `admin.jsx` — reception/admin panel

## Versioning (IMPORTANT — do this on every change)

Both apps have a hidden Easter egg (6 taps on the logo) that shows a
version number:

- `app.jsx` → `EasterEgg` component → `.ee-version` text
- `admin.jsx` → `AdminEasterEgg` component → `.ee-version` text

**Whenever you make ANY change to the web app** (either file, any
feature or fix), bump the version number in both places so it stays in
sync. Use a simple `vX.Y` scheme — bump the minor number for a normal
round of changes, the major number only for a large rewrite. Keep the
version identical in both `app.jsx` and `admin.jsx` (they're one
product, versioned together) even if a change only touched one of the
two apps.

## Other notes

- No build tooling — validate JS changes with `npx esbuild <file> --loader:.jsx=jsx --outfile=/tmp/out.js` before committing, since there's no compiler to catch syntax errors otherwise.
- **All work goes on `main`, and GitHub Pages publishes `main`**: a push is live in ~2 minutes, so test locally against the real base first (`PRUEBAS.md`). The old branch `claude/landing-page-implementation-lonkq` is history: never push to it.
- **The backend is the POS Supabase project**, not the old loyalty project (`config.js`). The schema lives there and is owned by the POS repo (`edgarmp25/app-padel-park`); this repo has no migrations. Shape changes vs. the old base are absorbed in `supabase-client.js` — read its header before touching data access.
- **The credential (`member_id`, `PP-AA-NNNNN`) is generated by the database.** Never invent one in the browser. A member's card is created or linked by `vincular_socio(p_nombre, p_telefono, p_birth)`.
- **Registration: whether there is a session after `signUp` decides the path, never a constant.** Since 26 Sep 2026 email confirmation is OFF in the POS project, so `signUp` returns a session and the card is created right there. If confirmation is ever turned back on, there is no session: the app says «Revisa tu correo» and the card is created on first login from the data stored in the account metadata. Both paths are live code; «correo sin confirmar» on login stays for the same reason (and for accounts created while it was on).
- **Linking an existing card needs the same email AND the same phone** (last 10 digits). `vincular_socio` has three refusals, all `P0001`, translated in `falloDeVinculo` (`app.jsx`): phone mismatch → the person fixes it on the same screen and retries (the account already exists: never send them to register again); card without phone, or several cards with that email → front desk. Anything else → the reason and a retry.
- **The visit cycle is computed in ONE place, and it is the database: `promocion_de(p_member_id)`** — the same function the POS calls (v3.4, 5 Oct 2026). `regla-visitas.js` is gone: it was a second copy that knew neither `reglas_promocion` nor its history. Every screen that talks about prizes reads `PPSb.promocionDe` and paints the jsonb's own keys — `participa`, `vinculado_en`, `visitas_cuentan`, `visitas[]` (`id, numero, dia, posicion, premio, regla_id`), `ciclo_actual` (`ciclo, visita_silver, visita_gratis, hechas`), `siguiente`, `proxima_con_premio`; premio is `'silver' | 'gratis' | null`: the member card, «Mis visitas», the panel's scan, the saved-visit screen and the member profile. **Nothing in the browser counts, walks or adjusts the cycle**: the dots come from `ciclo_actual` (`PPSb.puntosDelCiclo`), each visit's number and prize from `visitas` by id (`PPSb.porVisita`), and what the saved visit was is looked up **by the id the insert returned**. Never write a `% 7` or a cycle length again. **When the call fails the screen says it could not read the promotion (`PPSb.faltaPromocion`)** — never a cycle at zero, which a member reads as «nothing accumulated»; a `P0001` (no rule for a visit's day) says a rule is missing, not «check your connection». `scripts/contraste-promocion.mjs` compared the old copy against the function for every member before deleting it (12 of 12, read-only; it must fail with `--falsear` and `--vacia`).
- **The promotion counts visits since the member registered in the app (`members.vinculado_en`)** — decided by Edgar on 25 Sep 2026, and applied **inside `promocion_de`**. `PPSb.contarVisitas(memberId)` now counts only the total (the history and the tier, Bronce…Leyenda); when it differs from `visitas_cuentan`, `PPSb.lineaConteo` shows both. A member without `vinculado_en` (created at the front desk) **does not participate** (`participa: false`): never «0 visits».
- **A visit is inserted without `court`** (v3.4): nobody knows which court it was, the court lives in the POS booking. The panel no longer has a court selector. ⚠️ The column still defaults to `'01'`, so the base keeps writing it — that is pending SQL by Edgar (`docs/PROMPTS.md`), not something to patch from here.
- **«Miembro desde» reads `members.joined_at`** (`miembroDesde`, `app.jsx`): until v3.3 it read `member.joinedAt`, which doesn't exist, and painted «Invalid Date» on the profile and the downloadable card.
- **The member QR is `PPGJ|<credential>`, nothing else** (v3.3). It used to carry the name, which no reader uses and which made long-name QRs denser (25×25 modules without it, up to 37×37 with a 50-character name). Both readers — this panel's `parseQr` and the POS's `leerCodigoSocio` — still accept the old `PPGJ|<credential>|<name>`, which lives on downloaded cards and screenshots.
- **The panel cannot delete visits** (Edgar, 30 Sep 2026). A visit is deleted only from the POS, by `anular_visita`, which leaves a record in `anulaciones`. Once the DELETE policy on `visits` is dropped, a table delete would silently do nothing: `deleteVisit` and its button are gone on purpose. Don't put them back.
- **«Silver» names only the rate.** The member's tier by visits (`tierFor`: Bronce <10, Plata ≥10, Oro ≥25, Leyenda ≥50 — same thresholds as before, Spanish names since v3.2) keeps its CSS `key`s. And `members.level` is a third thing: playing level (Principiante, Intermedio…).
- **The reception panel logs in with a POS staff account** and checks `es_personal()`. There is no PIN.
- **No personal data leaves for a Google Sheet anymore.** Until v3.0 the sign-up form also posted name, email, phone and birthday to an Apps Script, guarded by a token published in `config.js`. Edgar turned it off on 26 Sep 2026: the data lives in the base, and the sheet was a copy behind a public password. `api.js`, `apps-script.gs`, `webhookUrl` and `sheetToken` are gone. **`config.js` carries nothing secret** — do not put a token back in it.
- **Nothing points to the old loyalty project (`fsuqslgmilyqkutyvvdl`) anymore**, in code or in the base: the 5 announcement images were copied byte for byte to the POS bucket on 26 Sep 2026 and `image_url` rewritten (`docs/imagenes-avisos-2026-09-26.md`, old → new). Only git history and that doc still name it. It can be shut down.
- Manual verification procedure: `PRUEBAS.md`. There is deliberately no automated test suite here — this app will be absorbed into the POS.
- Service worker (`sw.js`) uses network-first + active `registration.update()` checks on focus/visibility so installed PWAs pick up new deploys without a manual reinstall.
