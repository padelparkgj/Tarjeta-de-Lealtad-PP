# Padel Park Gran Jardín — Tarjeta de Lealtad

Loyalty card PWA for a padel club. Plain React 18 (UMD build) + Babel
standalone loaded via CDN `<script>` tags — no build step, no bundler.
One single-page app, on the POS's Supabase backend:

- `Landing Page.html` + `app.jsx` — member-facing app
- `Admin.html` — **a static page, not an app** (v3.7, 7 Oct 2026): it says the reception panel
  moved to the POS and links to `https://app-padel-park.vercel.app`. No Supabase, no script, no
  session. `admin.jsx`, `admin.css`, `admin-manifest.json` and `icons/admin-*` are gone.

## Versioning (IMPORTANT — do this on every change)

The app has a hidden Easter egg (6 taps on the logo) that shows a
version number: `app.jsx` → `EasterEgg` component → `.ee-version` text.

**Whenever you make ANY change to the web app** (any feature or fix),
bump it. Use a simple `vX.Y` scheme — bump the minor number for a normal
round of changes, the major number only for a large rewrite. Until v3.6
`admin.jsx` carried the same number; since v3.7 there is only one place.

## Other notes

- No build tooling — validate JS changes with `npx esbuild <file> --loader:.jsx=jsx --outfile=/tmp/out.js` before committing, since there's no compiler to catch syntax errors otherwise.
- **All work goes on `main`, and GitHub Pages publishes `main`**: a push is live in ~2 minutes, so test locally against the real base first (`PRUEBAS.md`). The old branch `claude/landing-page-implementation-lonkq` is history: never push to it.
- **The backend is the POS Supabase project**, not the old loyalty project (`config.js`). The schema lives there and is owned by the POS repo (`edgarmp25/app-padel-park`); this repo has no migrations. Shape changes vs. the old base are absorbed in `supabase-client.js` — read its header before touching data access.
- **The credential (`member_id`, `PP-AA-NNNNN`) is generated by the database.** Never invent one in the browser. A member's card is created or linked by `vincular_socio(p_nombre, p_telefono, p_birth)`.
- **Registration: whether there is a session after `signUp` decides the path, never a constant.** Since 26 Sep 2026 email confirmation is OFF in the POS project, so `signUp` returns a session and the card is created right there. If confirmation is ever turned back on, there is no session: the app says «Revisa tu correo» and the card is created on first login from the data stored in the account metadata. Both paths are live code; «correo sin confirmar» on login stays for the same reason (and for accounts created while it was on).
- **Linking an existing card needs the same email AND the same phone** (last 10 digits). `vincular_socio` has three refusals, all `P0001`, translated in `falloDeVinculo` (`app.jsx`): phone mismatch → the person fixes it on the same screen and retries (the account already exists: never send them to register again); card without phone, or several cards with that email → front desk. Anything else → the reason and a retry.
- **The visit cycle is computed in ONE place, and it is the database: `promocion_de(p_member_id)`** — the same function the POS calls (v3.4, 5 Oct 2026). `regla-visitas.js` is gone: it was a second copy that knew neither `reglas_promocion` nor its history. Every screen that talks about prizes reads `PPSb.promocionDe` and paints the jsonb's own keys — `participa`, `vinculado_en`, `visitas_cuentan`, `visitas[]` (`id, numero, dia, posicion, premio, regla_id`), `ciclo_actual` (`ciclo, visita_silver, visita_gratis, hechas`), `siguiente`, `proxima_con_premio`; premio is `'silver' | 'gratis' | null`: the member card, «Mis visitas» and the member profile (the panel's scan and saved-visit screen did too, until v3.7). **Nothing in the browser counts, walks or adjusts the cycle**: the dots come from `ciclo_actual` (`PPSb.puntosDelCiclo`) and each visit's number and prize from `visitas` by id (`PPSb.porVisita`). Never write a `% 7` or a cycle length again. **When the call fails the screen says it could not read the promotion (`PPSb.faltaPromocion`)** — never a cycle at zero, which a member reads as «nothing accumulated»; a `P0001` (no rule for a visit's day) says a rule is missing, not «check your connection». `scripts/contraste-promocion.mjs` compared the old copy against the function for every member before deleting it (12 of 12, read-only; it must fail with `--falsear` and `--vacia`).
- **The promotion counts visits since the member registered in the app (`members.vinculado_en`)** — decided by Edgar on 25 Sep 2026, and applied **inside `promocion_de`**. `PPSb.contarVisitas(memberId)` now counts only the total (the history and the tier, Bronce…Leyenda); when it differs from `visitas_cuentan`, `PPSb.lineaConteo` shows both. A member without `vinculado_en` (created at the front desk) **does not participate** (`participa: false`): never «0 visits».
- **This repo registers no visits** (v3.7): only the POS does (Socios → Registrar visita), with `court: null`. The member app only reads its own. ⚠️ `visits.court` still defaults to `'01'` — pending SQL by Edgar (`docs/PROMPTS.md`), not something to patch from here.
- **The general texts say the rule that applies TODAY, read from `regla_vigente()`** (v3.5): the welcome screen and Beneficios (`useReglaVigente`, `app.jsx`; `PPSb.reglaVigente`). It takes no arguments, `anon` can run it —the welcome screen has no session— and it returns one row `{ ciclo, visita_silver, visita_gratis, vigente_desde }` (an array from PostgREST; `.single()`). **No visit number of the rule is written in the code anymore**: if the read fails the screen says «Pregunta en recepción por la promoción vigente.» — never a fallback 4 and 7, which is the same lie under another name. ⚠️ **Don't use it for a member's own progress**: a member halfway through a cycle keeps the rule that cycle started with, so the card stays on `promocion_de` → `ciclo_actual`.
- **«Miembro desde» reads `members.joined_at`** (`miembroDesde`, `app.jsx`): until v3.3 it read `member.joinedAt`, which doesn't exist, and painted «Invalid Date» on the profile and the downloadable card.
- **A date without time (`date` column, `'YYYY-MM-DD'`) is shown through `PPSb.fechaSinHora`**, which splits year, month and day into a local date. `new Date('YYYY-MM-DD')` reads it as UTC midnight —the day before at the club— and that's why the birthday showed a day early on the member's profile until v3.5. Never add hours by hand (`+ 'T00:00:00'`). Today the only one painted is `birth`; `event_date` and `expires_at` are instants, not dates.
- **The member QR is `PPGJ|<credential>`, nothing else** (v3.3). It used to carry the name, which no reader uses and which made long-name QRs denser (25×25 modules without it, up to 37×37 with a 50-character name). The only reader left, the POS's `leerCodigoSocio`, still accepts the old `PPGJ|<credential>|<name>`, which lives on downloaded cards and screenshots.
- **«Silver» names only the rate.** The member's tier by visits (`tierFor`: Bronce <10, Plata ≥10, Oro ≥25, Leyenda ≥50 — same thresholds as before, Spanish names since v3.2) keeps its CSS `key`s. And `members.level` is a third thing: playing level (Principiante, Intermedio…).
- **No tournaments here** (v3.6, Edgar, 6 Oct 2026). Member tournaments are run in another app; in
  this one a `torneo` announcement is just an announcement — title, text, image, countdown — with
  **no signup button even if `allow_signup` is on**, no partner, no schedule, no results, no
  «Torneos» tab. Nothing reads or writes `tournaments`,
  `tournament_pairs` or `tournament_matches`, and `tournament-logic.js` and `whatsapp.js` are
  gone. **`signups` stays**: it is the signup to any announcement with `allow_signup` (a class, a
  clinic), not a tournament thing. Don't bring any of it back.
- **The reception panel is gone; reception is the POS** (v3.7, 7 Oct 2026). Everything it did —
  scan or type the credential and register the visit, history Hoy/Semana/Mes/Todo, the member
  list and search (also by email), the profile with each visit's number and prize, «Miembro
  desde» and the birthday month, the announcements and their signups— lives in the POS's Socios
  module (inventory in `docs/BITACORA.md`). **Nothing staff-only comes back here**: no
  `es_personal`, no member list, no visit insert, no announcement writes. `supabase-client.js`
  only has what the member app calls.
- **No personal data leaves for a Google Sheet anymore.** Until v3.0 the sign-up form also posted name, email, phone and birthday to an Apps Script, guarded by a token published in `config.js`. Edgar turned it off on 26 Sep 2026: the data lives in the base, and the sheet was a copy behind a public password. `api.js`, `apps-script.gs`, `webhookUrl` and `sheetToken` are gone. **`config.js` carries nothing secret** — do not put a token back in it.
- **Nothing points to the old loyalty project (`fsuqslgmilyqkutyvvdl`) anymore**, in code or in the base: the 5 announcement images were copied byte for byte to the POS bucket on 26 Sep 2026 and `image_url` rewritten (`docs/imagenes-avisos-2026-09-26.md`, old → new). Only git history and that doc still name it. It can be shut down.
- Manual verification procedure: `PRUEBAS.md`. There is deliberately no automated test suite here — this app will be absorbed into the POS.
- Service worker (`sw.js`) uses network-first + active `registration.update()` checks on focus/visibility so installed PWAs pick up new deploys without a manual reinstall.
- **When files leave the site, bump `CACHE` in `sw.js`.** Network-first means online devices already get the new page, but the cache keeps whatever it ever stored, and offline it serves it: with `ppgj-v3`, a device that had the panel still got `admin.jsx` with `200` offline after v3.7 was published. A new name makes `activate` delete the old cache (measured in the bitácora, v3.7). Only `Landing Page.html` registers `sw.js`; `Admin.html` stays under it because the scope is the folder.
